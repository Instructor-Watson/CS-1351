# Personal Project Planning Guide

Use this guide with ProjectProposal.md. A strong proposal describes a small program that can be completed with the Java concepts taught in this course.

## 1. Define one user and one problem

Name the person who will use the program and the specific problem it solves. Avoid broad goals such as “help everyone stay organized.” Prefer a concrete statement such as “help a student keep and review a short list of study tasks.”

## 2. Describe the Part 1 workflow

Write the user's experience from start to finish:

1. What the program displays first.
2. What the user enters.
3. What decision or processing occurs.
4. What data is stored.
5. What result is displayed.
6. How the program ends.

Keep Part 1 small enough to finish in Week 10. One complete workflow is better than several unfinished features.

## 3. Map each Java concept to a feature

Do not merely list terms. Explain the job each concept performs in your program. For example, “a loop repeats the menu until the user chooses Quit” is specific; “the project uses a loop” is not.

Part 1 must map console input/output, variables, an if/else-if/else decision, relational and logical operators, a loop, two methods besides main, and an array.

## 4. Plan Part 2 improvements

Choose a useful role for each later concept:

- String manipulation changes, searches, formats, or analyzes project text.
- Loop-based validation explains invalid input and asks again until the input is valid.
- An array or ArrayList stores related data and supports a meaningful operation such as adding, listing, searching, sorting, or removing.

## 5. Give testable examples and a realistic timeline

For each of three examples, name an exact input and the expected result. Include at least one normal workflow and one boundary or invalid-input case.

Plan a small result for each period: design and prototype in Weeks 8-9, complete Part 1 in Week 10, add one improvement at a time in Weeks 11-14, and reserve Week 15 for integration, testing, documentation, and presentation.

## 6. Identify risks and fallback scope

Name at least two realistic difficulties. For each, state a smaller version that still completes the program's main purpose. A fallback removes a feature; it does not remove a required Java concept.

## Final proposal check

- The intended user and problem are specific.
- The Part 1 workflow has a clear beginning, middle, and end.
- Every required Java concept has a concrete job.
- Part 2 additions fit the same program.
- Three examples include exact expected results.
- The file list and timeline are realistic.
- Two risks each have a workable fallback.
- No TODO markers remain.
